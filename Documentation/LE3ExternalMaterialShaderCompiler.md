## Goal and safety boundary

Input is a loaded LE3 `Material` or `DecalMaterial` export whose authored expression graph is present. Future MaterialInstance requests will resolve to that base graph plus a merged static parameter set; the resolved-input hook is implemented, not the instance resolver. The eventual output is:

1. LE3-compatible generated `Material.usf` HLSL.
2. The exact shader-type and vertex-factory permutations selected by the engine's three `ShouldCache` gates.
3. D3D SM5 bytecode and reflected `FParameterAllocation` data for each permutation.
4. A complete `FMaterialShaderMap` and shader-cache representation that LEC can serialize and install.

Unsupported expressions, unregistered shader types, and unresolved cache predicates must fail explicitly. Do not infer a complete shader set from a reference cache or write generated maps into packages until shader-map construction and round-trip validation are complete.

The implementation lives in the standalone `LegendaryExplorerCore.Shaders.LE3MaterialShaderCompiler` class. It is deliberately independent of WPF and of the in-game ShaderClient.

The user also supplied the UE3 reference source at `S:\Src\InfinityBlade\UnrealEngine3-10897\Development\Src`. It is useful for locating intended material rules but is a different engine revision; a rule is LE3-confirmed only after matching the shipping LE3 executable or native captures.

Performance boundary: the compiler already avoided pixel decoding and mip/binary parsing, but previously required loaded texture export data for property access and resolved exports for imports. The metadata-only input removes that requirement. The property-only reader below now supplies it with a per-session cache, and a limited real-package comparison is recorded under Verification. ### Property-only package reader and cache

`LE3TextureMetadataReader` is a separate, read-only **LE3 PC** session:

- `Open(packagePath)` owns a read-only file handle; the stream constructor supports a readable/seekable source positioned at zero with explicit `leaveOpen` ownership. Both use the existing lazy package/table/decompression reader rather than duplicate package parsing.
- `Read(exportUIndex)`, `Read(instancedFullPath)`, and `Read(export)` obtain metadata from a bounded view of the original serialized export. They parse properties through the top-level `None` terminator without allocating/installing the export data or decoding texture binary/mips. They reject nontexture exports, foreign package references, malformed/unterminated property lists, and wrong types for the relevant metadata fields. Failures are not cached as successes/defaults.
- Successful metadata is cached per export inside the session. Cache hits return the same immutable metadata object with no further source reads. The cache is package-qualified by its owning session, not process-global or persistent. Source package/headers must not change during the session. Create a new reader after edits; the cache has no automatic invalidation.
- `Package` exposes the lazy header/table package, allowing callers to load only their material/expressions when the graph is local. This is an unsafe advanced package view: **do not save or edit it**, do not concurrently use its source, and keep the reader alive during reads. Original on-disk data, not any in-memory export edits, is authoritative for the reader.
- Import discovery is still caller-owned. Use the import locator to choose the proper donor reader and export path/UIndex, then feed its metadata through `getTextureMetadata`. Never pass a negative import UIndex straight to a donor's `Read(int)` or confuse UIndexes between sessions. Returned metadata does not replace the graph's original reference.
- `ILazyLoadPackage.OpenExportDataStream(export)` is the narrow reusable package hook: a relative-position, read-only, export-bounded stream that leaves the package source open when disposed and supports serially interleaved views. `MEPackage` implements it using `BoundedReadOnlyStream`; ownership and bounds are validated. Existing `LoadExport` behavior is unchanged.
- The reader/stream are not thread-safe. Use separate sessions per concurrent worker. Compression blocks can include adjacent binary data; unusual table layouts can make the existing decompressor fall back to wider decompression. The optimization avoids export-sized buffers; its physical I/O benefit depends on package layout and source stream type.

Local-reference usage (an import callback would instead locate a donor session/export):

```csharp
using var reader = LE3TextureMetadataReader.Open(packagePath);
var material = reader.Package.LoadExport(materialUIndex);
// Load the selected expression graph separately; leave texture exports unloaded.
var compiler = new LE3MaterialShaderCompiler(material,
    getTextureMetadata: reference => reader.Read(reference.UIndex));
```
